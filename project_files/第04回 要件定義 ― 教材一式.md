# 【第04回】01_トークスクリプト

## 第4回 トークスクリプト（講義22分）

### ①機能要件と非機能要件（12分）
「前回集めた『願い』を、今日は『合意できる仕様』に変えます。その第一歩が仕分けです。要件は2種類に分かれます。**機能要件**は『システムが何をするか』。注文できる、売上を集計できる。動詞で書けるものです。**非機能要件**は『どの程度うまくやるか』。3秒以内に表示、昼休み中は止まらない、個人情報を守る。品質の条件です。」
「初心者が必ずやる失敗を言います。**非機能要件を忘れる**。機能は顧客が口にしてくれますが、非機能は口にされないことが多い。『速く』『ちゃんと』という曖昧な言葉の正体が実は非機能要件です。皆さんの記録シートにも『速くしてほしい』がありましたね？　あれを『注文から受取まで10分以内』のような測れる形にするのが今日の仕事です。非機能の代表分類は、性能・可用性・セキュリティ・運用。この4分類は暗記してください。」

### ②要件定義書：合意の証拠（10分）
（スライド：テンプレの目次）
「要件定義書は『顧客と開発者が、これを作ると合意した証拠』です。テキストの記述例（該当ページを板書）を開いてください。項目立てを見ると、目的、用語定義、機能要件一覧、非機能要件、前提・制約、そして**今回やらないこと**。最後の『やらないこと』が意外に大事です。書いておかないと、納品直前に『え、それも入ってると思ってた』が起きます。」
「もう1つ、テンプレの機能要件一覧に『要求No』の列があります。これは**トレーサビリティ**——どの要求からこの機能が生まれたかの追跡線です。今日から全成果物でIDをつなげていきます。最終回まで続く伏線なので、面倒でも必ず埋めてください。それから、皆さん気づいていますか。スタッフは『紙でも出してほしい』、運営は『ペーパーレスにしたい』と言っていました。**要求は矛盾する**んです。全部は叶えられない。だから優先度を付けます。Must・Should・Could・Won't の4段階。ではやってみましょう。」

# 【第04回】04_配布_あいまい表現チェックリスト（配布資料）

## あいまい表現チェックリスト（ペアレビュー用）
相手の要件定義書で以下のNGワードを探し、コメント（提案モード）で修正案を添える。最低3件。

| NGワード | なぜダメか | 直し方の例 |
|---|---|---|
| 速く／すぐに | 人により基準が違う | 「メニュー一覧を3秒以内に表示」 |
| 使いやすく | 測れない | 「注文完了まで3タップ以内」 |
| ちゃんと／適切に | 中身がない | 「個人情報は暗号化して保存」 |
| なるべく／できるだけ | 実施条件が不明 | 「必須」か「対象外」かを決める |
| たくさん／大量 | 数が不明 | 「同時接続100人」 |
| 柔軟に | 何がどう変わるのか不明 | 変更されうる項目を列挙する |

追加観点：□ 機能要件が動詞で書けているか ／□ 要求No（トレース元）が埋まっているか ／□「やらないこと」が空欄でないか

# 【第04回】05_小テスト

## 小テスト③（第3章前半範囲）※各2点
1. 「要求」と「要件」の違いの説明として正しいものは？ a) 同じ意味 b) 要求=顧客の願い、要件=合意した仕様 c) 要件=顧客の願い、要求=合意した仕様 → **b**
2. ヒアリングで「速くしてほしい」と言われた時の最適な返しは？ a) 分かりましたと答える b) 「例えば何秒以内なら良いですか」と具体化する c) 無視する → **b**
3. 要求を聞くべき相手として不適切なのは？ a) 利用者 b) 運用担当 c) 関係のない他社の顧客 → **c**
4. 「何をしたい」に加えて必ず聞くべきものは？（記述）→ **何のために（目的）**
5. 複数の関係者の要求が食い違った場合、まず行うべきことは？ a) 全部作る b) 優先度を付けて合意を取る c) 聞かなかったことにする → **b**
