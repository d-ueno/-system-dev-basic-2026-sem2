# 【第02回】01_トークスクリプト

## 第2回 トークスクリプト（講義25分）

### ①開発モデル＝「進め方の型」（10分）
（スライド：滝の図）
「家を建てるとき、基礎→柱→屋根→内装と、後戻りしない順で進めますね。ソフトウェアでこれをやるのが**ウォーターフォール型**。要求→設計→製造→テストと、水が滝を落ちるように一方向に進みます。長所は、計画が立てやすく、大人数の分担がしやすいこと。短所は、後半で『やっぱり違う』となった時の手戻りが高くつくこと。」
（スライド：らせん→小さいループの図）
「対して**アジャイル型**は、小さく作って見せて直す、を繰り返す型。詳しくは第13回でやるので、今日は『型が複数あり、案件によって使い分ける』ことだけ覚えてください。この授業では前半、ウォーターフォールを深掘りします。理由は単純で、工程と成果物の対応が一番はっきりしていて、学ぶ土台に最適だからです。」

### ②なぜルール（作業標準）が要るのか（8分）
「質問です。『ログイン』と『サインイン』、同じ文書に混ざっていたらどう感じますか？　読む側は『別の機能か？』と疑い、確認の時間が発生します。100ページの設計書で用語がバラバラだったら？　だから現場には**作業標準**があります。用語を統一する、工程の名前と作る文書を決めておく、図の書き方を揃える。地味ですが、これは『他人が読む』ためのマナーであり、品質そのものです。先週のFigJamで、同じものを違う言葉で書いた付箋がありましたよね。あれが用語ゆれの正体です。」

### ③チャート記法：今日の主役（7分）
（スライド：記号一覧）
「今日はフローチャートを書けるようになって帰ります。記号は実質5つ。端子・処理・判断・入出力・線。ルールは3つだけ。**上から下へ／判断には条件とYes・Noを書く／線は交差させない**。なぜ図にするのか？　文章の『適宜対応する』は人によって解釈が割れますが、図の分岐は割れません。この後、皆さんのチャートが本当に『割れない』か、ペアで検証実験をします。」

# 【第02回】02_配布_drawio入門ガイド（配布資料）

## diagrams.net（draw.io）入門ガイド
1. app.diagrams.net を開く → 保存先「Google Drive」→「新規作成」→ファイル名 `第2回_課題1_氏名`
2. 図形：左パレットからドラッグ。ダブルクリックで文字入力
3. 線：図形の縁にマウス→青い矢印が出たらドラッグで接続（図形を動かしても線が追従する「接続」を必ず使う）
4. フローチャート記号：左パレット検索欄で「flowchart」
5. 保存は自動。提出＝ファイルを「02_提出/第2回」フォルダへ移動

### 作図の約束（規約）
上から下へ／判断（ひし形）には条件を書き、出る線に Yes・No を書く／線は交差させない／開始と終了の端子を必ず置く／1つの箱に1つの動作

# 【第02回】03_配布_演習課題（配布資料）

## フローチャート演習課題

### 課題1「朝起きてから家を出るまで」（20分）
自分の実際の行動をフローチャートにする。10〜15個の箱を目安。
ヒント：「準備する」は1つの箱にしない（何を？と聞かれる粒度はNG）

### 課題2「自販機でジュースを買う」（12分）
必ず判断（分岐）を2つ以上入れること。
考慮すべき状況：お金が足りない場合／売り切れの場合（他の考慮があれば追加してよい）

### ペア検証（あいまいさ実験）の手順
1. 指定されたペアの提出ファイルを開く
2. 相手のチャートを上から指でなぞり、「その通りに」動けるか頭の中で実行する
3. 検証フォームに回答：Q1 最後まで迷わず動けたか（はい/いいえ）／Q2 迷った箇所の文言をそのまま転記／Q3 どう直せば迷わないか提案

# 【第02回】04_小テスト

## 小テスト①（第1章範囲）※Googleフォーム化・各2点・10点満点
1. ソフトウェア開発に工学的アプローチが必要になった主な理由を1つ選べ。
   a) コンピュータが高価だから b) 大規模化・多人数化で個人技では品質が保てないから c) 法律で義務だから → **b**
2. 開発の各工程で作られる文書や図などを総称して何と呼ぶか（記述）→ **成果物**
3. 「何を作るかを決める」工程と「どう作るかを決める」工程、先に行うのはどちらか → **何を作るかを決める工程**
4. ウォーターフォール型の特徴として正しいものを選べ。
   a) 工程を行き来しながら進める b) 工程を一方向に順に進める c) 設計を省略する → **b**
5. 成果物（文書）を作る最大の目的は次のうちどれか。
   a) 作業の証拠を残すため b) 次の工程・他人へ正確に引き継ぐため c) 顧客に厚い納品物を見せるため → **b**

# 【第02回】90_講師用_悪い例と解説（講師用（非公開））

## 講師用：フローチャート悪い例（実演修正用）
まとめの6分で投影し、その場で直して見せる。

悪い例の仕込み（1枚のdrawioに以下を含めて事前作成）：
1. 判断記号に条件が書かれていない（「チェック」とだけ）→ 条件「残高≧価格?」に修正、Yes/Noを付ける
2. 線が交差している → 配置替えで解消
3. 終了端子がない → 追加
4. 「対応する」という曖昧な処理箱 → 「エラーメッセージを表示する」に具体化
5. 1つの箱に「お金を入れてボタンを押す」→ 2つに分割

曖昧表現ランキングの作り方：検証フォームQ2の回答を単語で集計し上位5つを投影（例年「準備する」「確認する」「ちゃんと」が上位）。
