# 【第07回】01_トークスクリプト

## 第7回 トークスクリプト（講義20分）

### ①内部設計：開発者のための設計（8分）
「先週まで作っていた外部設計は『利用者に見せる図面』でした。今日からの**内部設計**は『作る人のための図面』です。家で言えば、配線図・配管図。住む人は見ませんが、これがないと大工さんは作れない。読者が変わるので、書く内容も変わります。外部設計書に『ボタンの色』を書き、内部設計書に『データの持ち方・処理の手順』を書く。」
「内部設計の二本柱は、**機能をどう部品に分けるか**（プログラムの部品化・構造化）と、**データをどう持つか**（データ設計）。今日は後者、データ設計を集中的にやります。」

### ②データ設計：システムの記憶を設計する（12分）
「システムは記憶がなければ何もできません。注文を受けても保存しなければ、厨房には何も届かない。その記憶の置き場が**テーブル**——行と列でできた表です。」
「テーブルを見つける実践的な方法を教えます。**名詞抽出法**。自分たちの要件定義書・外部設計書から名詞を拾う。学生、メニュー、注文、残数、売上……。次に『保存が必要か』でふるいにかける。画面に一瞬表示するだけの計算結果は保存不要、注文の記録は保存必須。残った名詞がテーブルの候補です。」
「テーブル定義で決めるのは、項目名・型・キー。**主キー（PK）**は行を一意に特定する背番号——注文IDのような。**外部キー（FK）**は他のテーブルへの参照——注文テーブルが『どの学生の注文か』を学生IDで指す。この線のつながりがデータ設計の骨格です。」
「1つだけ、今日皆さんがぶつかる名物問題を予告します。『1回の注文でカレーとうどんを両方頼んだら、注文テーブルにどう入れる？』——列を増やす？行を増やす？ 正解は授業の最後に。まず自分たちの案で作ってみてください。」

# 【第07回】90_講師用_模範テーブル構成（講師用（非公開））

## 講師用：模範テーブル構成（4テーブル）※ハンズオン後に公開
1. **学生（student）**：student_id(PK)／氏名／プリペイド残高
2. **メニュー（menu）**：menu_id(PK)／メニュー名／単価／当日残数／提供可否フラグ
3. **注文（order）**：order_id(PK)／student_id(FK)／注文日時／受取番号／状態（受付/調理中/受取可/受取済）
4. **注文明細（order_detail）**：order_id(FK)＋明細No(PK複合)／menu_id(FK)／数量／注文時単価

### 名物問題の解説トーク
「カレーとうどんを1回で注文——注文テーブルに menu_id1, menu_id2… と列を増やした人？　3品頼まれたら列が足りませんね。**繰り返すものは行にする**。だから注文（1回分のヘッダ）と注文明細（品目ごとの行）に分けます。帳票のヘッダと明細、同じ構造だと気づいた人は鋭い。」
「もう1つ、明細に『注文時単価』を持つ理由：メニューの価格が改定されても過去の注文金額が変わらないようにするため。データは歴史を記録します。」
