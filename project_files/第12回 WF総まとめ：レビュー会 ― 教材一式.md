# 【第12回】01_トークスクリプト

## 第12回 トークスクリプト（作法説明8分＋締め5分）

### レビュー会の作法（8分）
「今日は講義なし。皆さんが9回かけて作った成果物一式——要求リストから、要件定義書、外部・内部設計書、テスト仕様書、カバレッジ表まで——を、互いにレビューします。実務のレビュー会と同じ作法でやります。5か条。**人ではなく成果物に指摘する**。『君はダメ』ではなく『この期待結果は曖昧』。**代替案を添える**。**良い点も必ず1つ言う**。**指摘された側は反論より先にメモ**。**全部は直さない**——重大度を付けて、直す価値のあるものから。指摘は記録票へ。件数を競う場ではありませんが、指摘ゼロは『読んでいない』のと同じです。」

### 締め：手戻りの経済学（5分）
「最後に見てもらった波及図。要件の1行の曖昧さが、画面を変え、テーブルを変え、テストを全部やり直させる。業界でよく引かれる経験則に、**欠陥の修正コストは工程が進むほど桁で増える**というものがあります。要件段階なら打ち合わせ1本。総合テストで見つかれば設計からやり直し。リリース後なら謝罪から始まる。だからウォーターフォールは各工程でレビューを重ね、文書で合意を固めながら進むのです。」
「……ただし。『そもそも最初に全部を正しく決められるのか？』という疑問を持った人はいませんか。顧客も、作る前は本当に欲しいものが分からないことがある。その疑問への1つの答えが、次回からの**アジャイル型開発**です。」

# 【第12回】04_配布_レビューマナー5か条（配布資料）

## レビューマナー5か条（常時投影スライド原稿）
一、人ではなく成果物に指摘する
二、「ダメ」ではなく「こうしては」——代替案を添える
三、良い点も必ず1つ言う
四、指摘された側は、反論より先にメモ
五、重大度を付ける——全部直さない判断も設計のうち

# 【第12回】06_配布_波及トレースワーク（配布資料）

## 波及トレースワーク（FigJamボード原稿）
4段フレームを縦に配置：①要件定義書 → ②外部設計 → ③内部設計 → ④テスト
- 最上段に「上流の誤り・曖昧さ」1件を置く（例：第3回に仕込まれていた『注文票は紙で欲しい(スタッフ) vs ペーパーレス(運営)』の矛盾。自Gで見つかった実例でも可）
- 各段に「影響を受ける成果物と修正内容」を付箋で置き、矢印（コネクタ）でつなぐ
- 最下段の下に記述枠：「この誤りが総合テストで初めて発覚した場合、どの成果物を作り直すことになるか」
